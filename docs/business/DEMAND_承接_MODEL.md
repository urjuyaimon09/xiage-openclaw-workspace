# 需求承接模型

本文档与 `DEMAND_MODEL.md` 同级平行，共同构成三层架构的业务层。

## 一、定位

| 文档 | 职责 |
|------|------|
| DEMAND_MODEL.md | 把输入转化为需求清单（定义"要什么"） |
| **DEMAND_承接_MODEL.md** | 把需求清单转化为执行方案并完成验收（定义"怎么做"） |

两者是协作关系，不是上下游关系。

---

## 二、三方结构

| 角色 | 职责 |
|------|------|
| **需求方**（坚果） | 提出需求，确认验收标准，最终审批 |
| **承接方**（虾哥） | 接收需求，制定执行方案，执行并自检 |
| **裁判方**（独立机制） | 验证执行结果是否符合验收标准，**不能与承接方重叠** |

**关键原则：运动员不能是裁判。**

---

## 三、需求具体化（阶段一：接收）

收到需求后，第一步不是拆解方案，是先把需求具体化：

| 要素 | 说明 |
|------|------|
| **目标** | 要什么（最终状态是什么） |
| **方法** | 用什么方式实现（脚本/skill/人工执行…） |
| **量** | 量化指标（时间/次数/级数…） |
| **验收条件** | 可测试、可观测的结果 |

- 验收条件必须具体到可以判断"做到了"还是"没做到"
- 如验收条件模糊 → **反馈给需求方澄清**，不能自行假设

---

## 四、承接方案生成（阶段二：执行）

方案不止一种，每条需求至少生成 **2 个以上**可行方案：

| 方案类型 | 说明 |
|---------|------|
| **现成方式** | 咨询 skill-roundtable、头脑风暴等已有方式 |
| **自建 skill** | 自行搭建 skill 实现 |
| **指导+执行** | 虾哥出指导方案，坚果人工执行 |
| **混合方案** | 以上组合 |

- 方案需标注：投入成本（token/时间）、预期收益、风险评估
- 坚果在概念阶段 CDCP 决策时选定方案

---

## 五、IPD 六阶段方法论

| 阶段 | 关键活动 | 核心产出 |
|------|---------|---------|
| **概念CDCP** | 需求具体化、方案生成、收益/成本分析 | **概念决策包**：值不值得做？选哪个方案？ |
| **计划PDCP** | 细化方案、资源评估、TR1评审 | 执行计划：怎么做、谁做、多久 |
| **开发TR3** | 设计与实现、单元测试 | 可交付物 |
| **验证TR6** | 裁判方验收测试 | 验收结论 |
| **发布ADCP** | 交付、确认 | 闭环 |
| **生命周期** | 维护、迭代、退市 | 持续运营 or 退场 |

**CDCP 是整个模型的决策枢纽。**

---

## 六、项目类型分支

### A类：商业项目

在概念阶段完成四算：
- **市场需求**：规模、定价、区域分布
- **目标成本**：BOM + 研发摊销 + 制造 + 售后
- **资源投入**：人月、费用、物料
- **利润测算**：IRR / ROI / NPV / 回收期

→ CDCP 决策：财务指标达标则启动，不达标则砍

### B类：其他项目（情绪价值/社交类）

在概念阶段完成定性判断：
- **收益类型**：情绪价值、社交价值、能力建设…
- **成本估算**：时间、token、精力
- **性质结论**：值得做 / 不值得做 / 条件值得做

→ CDCP 决策：收益覆盖成本则启动

**WoW脚本属于B类。**

## 七、三阶段主流程

```
阶段一：接收
  → 接收需求清单
  → 需求具体化（目标/方法/量/验收条件）
  → 验收条件模糊 → 反馈需求方澄清

阶段二：执行
  → 生成 2+ 个可行方案（现成/自建/指导+执行/混合）
  → 执行 CDCP 概念决策（坚果拍板）
  → 选定方案后执行
  → 自检（不是裁判）
  → 提交裁判方验收

阶段三：验收
  → 裁判方验证（按验收条件）
  → 通过 → 闭环
  → 不通过 → 打回阶段二
```

---

## 八、与 DEMAND_MODEL.md 的接口

需求清单中每条需求，承接时需完成：
1. 识别项目类型（A类/B类）
2. 执行 CDCP 概念决策
3. 进入对应分支流程
