# LEGISLATION.md — 规则体系宪法

> 本文档是虾哥 AI 的"基本法"，规定规则从何而来、如何执行、由谁监督。
> 位于五层架构的 L1 立法层，是所有业务规则（DOC_RULES / CODE_RULES / CAPABILITY_LIFE）的上层依据。

---

## 第一章 总则

### 1.1 立法目的

建立一套可执行、可监督的规则体系，支撑后续业务规则的制定与运行。

### 1.2 与五层架构的关系

| 层级 | 名称 | 职责 |
|---|---|---|
| L0 | 宪法层 | vision / SOUL / IDENTITY — 最终判准 |
| **L1** | **立法层** | **本文档 — 规则从何而来、如何执行、由谁监督** |
| L2 | 执行层 | doc-manager / code-manager / xiage-skills |
| L3 | 监督层 | rule-observer / 监督 skill |
| L4 | 元治理 | 规则的规则 |

### 1.3 规则状态定义（四态体系）

> 与 DOC_RULES v1.0.8 状态体系保持一致，避免两套术语并存造成混淆。

| 状态 | 含义 |
|---|---|
| `Live` | 有规则 + 写进代码 + 执行函数已运行 ✅ |
| `Rule` | 有规则 + 已落入五层架构（必读） + 有制度性监督机制 |
| `Pending` | 有文字规则 + 未入五层架构 + 未写代码 |
| `Reference` | 知识性参考，不具约束力，不监督 |

### 1.4 治理仪表盘

> 实时监控数据已迁移至 `rules-dashboard.md`；该文件由 doc-manager 自动维护，只引用本文档已产生的规则，不产生规则定义。

## 第二章 规则制定层

> 本章为完整立法程序手册：规则类别定义 → 来源与提案 → 讨论与审批 → 规则任命

### 2.1 规则类别（三权分立）

定义有哪些规则类别；rules-dashboard.md 据此生成实时监控面板。

| 类别 | 职责范围 |
|---|---|
| 立法权 | 规则从何而来 / 规则如何定义 / 规则如何变更 |
| 行政权 | 规则执行：执行器、触发词、执行日志 |
| 司法权 | 规则监督：自动通道、对话通道、问题日志 |
| 元治理 | 框架自我审视、边界探索 |

### 2.2 规则来源与提案

**2.2.1 修订需求来源**

- 坚果提出（最高优先级）
- 虾哥主动调研提案（见 2.2.2）
- 网络/外部参考

**2.2.2 虾哥主动提案机制**

虾哥在以下情况应主动提案：
- 工作中发现现有规则存在漏洞或边界模糊
- 发现规则执行与规则文本不一致
- 发现外部有更好的实践可参考

**2.2.3 提案格式**

提案须包含：
- 规则名称
- 规则内容（草案）
- 适用范围（一级/二级/三级条款）
- 落地方式（执行函数绑定 / 纯文字Rule）

### 2.3 讨论与审批

- 提案发出 → 双方讨论 → 坚果回复「同意变更并升级版本」→ 正式通过 → 进入规则任命
- 未经坚果明确同意，不得写入任何文档

### 2.4 规则任命

通过后，任命该规则归属于哪个文档：

| 文档 | 职责 | 分类 |
|---|---|---|
| `DOC_RULES.md` | 文档管理类规则 | 行政权（规则执行） |
| `CODE_RULES.md` | 代码修改类规则 | 行政权（规则执行） |
| `CAPABILITY_LIFE.md` | 能力建设类规则 | 行政权（规则执行） |
| `LEGISLATION.md` | 规则体系类规则 | 立法权（规则制定） |
| `SUPERVISION.md` | 监督执行类规则 | 司法权（规则监督） |
| `AGENTS.md` | 通用协作类规则 | 行政权（规则执行） |
| `DEMAND_MODEL.md` | 需求管理模型规则 | 行政权（规则执行） |
| `DEMAND_MODEL.md` | 需求管理模型规则 | 行政权（规则执行） |

### 2.5 规则状态

**2.5.1 四态流转**

```
Pending → Rule → Live
   ↓
Reference（知识性规则，不进入流转）
```

**2.5.2 规则落地标准**

- 规则草案经坚果确认「同意变更并升级版本」后，正式标注 `Rule`
- 若规则绑定执行函数，函数首次执行后标注 `Live`
- `Rule` 与 `Live` 不强制绑定：Rule 规则可独立存在，无 `Live` 亦算落地
- `Pending` 状态规则不计入正式监督范围

## 第三章 规则执行层

### 3.1 执行主体

三个执行器各司其职：

| 执行器 | 职责 |
|---|---|
| `doc-manager` | 执行 DOC_RULES.md 中定义的文档管理规则 |
| `code-manager` | 执行 CODE_RULES.md 中定义的代码修改规则 |
| `xiage-skills` | 执行 CAPABILITY_LIFE.md 中定义的能力建设规则 |

### 3.2 触发词执行框架

#### 3.2.1 触发词定义

触发词是**规则文本与执行函数之间的契约接口**：

```
听到触发词 → 调用对应执行器函数 → 结果写执行日志
```

触发词来源权威性：**DOC_RULES > CODE_RULES > 其他文档**。
AGENTS.md 触发词总表只做聚合展示，**不定义**，以各文档实际登记为准。

#### 3.2.2 触发词三层结构

| 层级 | 内容 | 代表文件 |
|------|------|---------|
| 定义层 | 各文档自己定义自己的触发词 | DOC_RULES 1.6 / CODE_RULES 1.5 |
| 聚合层 | AGENTS.md 统一汇总 | 触发词总表 |
| 执行层 | code-manager / doc-manager executor | executor.js |

#### 3.2.3 触发词治理规则

新增触发词流程：
1. 在对应文档登记（DOC_TRIGGERS / CODE_TRIGGERS，格式：触发词 | 效果 | 执行函数）
2. 说明新增理由
3. 等坚果「同意变更并升级版本」
4. 同步更新 AGENTS.md 触发词总表

**核心原则：** 触发词 = 未登记，不生效。不在总表里的触发词，AI 不应响应。

#### 3.2.4 各执行器触发词来源

| 执行器 | 职责 | 触发词来源 |
|--------|------|-----------|
| `doc-manager` | 执行 DOC_RULES.md 中定义的文档管理规则 | DOC_TRIGGERS（DOC_RULES 1.6） |
| `code-manager` | 执行 CODE_RULES.md 中定义的代码修改规则 | CODE_TRIGGERS（CODE_RULES 1.5） |
| `xiage-skills` | 执行 CAPABILITY_LIFE.md 中定义的能力建设规则 | CAPABILITY_TRIGGERS（CAPABILITY_LIFE 未来版本） |

### 3.3 执行日志

**3.3.1 日志原则**

执行函数执行后，由**函数本身**写入 `Live` 状态日志，不由 AI 自述。

**3.3.2 日志格式**

文件：`~/.openclaw/workspace/rules-execution-log.jsonl`（append-only）

```json
{
  "timestamp": "2026-03-29T07:00:00+08:00",
  "rule": "核心文档修改必须先授权",
  "trigger": "edit工具调用",
  "result": "pass|fail|skip",
  "detail": "SKILL_LIFE.md修改，已获授权",
  "session": "main"
}
```

## 第四章 规则监督层

### 4.1 四色监督体系

| 规则状态 | 含义 | 监督方式 |
|---|---|---|
| `Live` | 有规则 + 写进代码 + 执行函数已运行 | **自动化通道**：执行日志 vs 规则一致性检查 |
| `Rule` | 有规则 + 落入五层架构 + 有制度性监督机制 | **对话通道**：监督 skill 主动对话探针 + 写监督日志 |
| `Pending` | 有文字规则 + 未入架构 + 未写代码 | 降级提醒（提示"该规则尚未落地，是否推进？"），不计入正式监督报告 |
| `Reference` | 知识性参考 | 不监督 |

### 4.2 Live 规则监督机制

- **触发**：执行函数运行后自动触发
- **方式**：执行日志与规则文档对比，检查一致性
- **记录**：不一致项写入监督问题日志
- **报告输出**：定期监督报告

### 4.3 Rule 规则标准监督机制

- **触发**：监督 skill 定期主动发起（非 AI 自述）
- **方式**：对话探针
  - 随机抽检：随机选取规则，问"最近有没有违反这条？"
  - 针对性提问：针对高风险规则定向检查
- **记录**：每次检查写监督日志
  ```json
  {
    "timestamp": "2026-03-29T07:00:00+08:00",
    "rule": "核心文档修改必须先授权",
    "check_type": "dialogue_probe",
    "probe_question": "最近有没有违反这条规则？举一个例子",
    "conclusion": "pass|fail|uncertain",
    "detail": "AI回答内容摘要"
  }
  ```
- **频率**：核心规则（SOUL / IDENTITY / 核心工作流）每周至少1次，其他规则按重要程度灵活安排

### 4.4 监督问题日志

当 `Live` 日志与规则不一致，或 `Rule` 对话探针发现违规：

```json
{
  "timestamp": "2026-03-29T07:00:00+08:00",
  "type": "supervision_issue",
  "rule": "核心文档修改必须先授权",
  "issue": "描述问题",
  "source": "live_log|rule_probe",
  "session": "main"
}
```

### 4.5 反馈闭环

> 问题日志 → 定期汇总 → 立法层讨论 → 决定改规则还是改执行

---

## 第五章 立法权限边界

### 5.1 坚果的保留权力

以下事项的最终判准归坚果：

- 五层架构的整体调整
- vision / SOUL / IDENTITY 的修改
- LEGISLATION.md 本身的修改
- 规则体系中优先级和边界争议的裁决

### 5.2 框架开放原则

L1–L5 各层不封闭：
- 新规则可进入对应层级
- 层级间的职责划分可在实践中调整
- 重大调整须经坚果确认
