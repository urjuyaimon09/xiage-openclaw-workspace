# CAPABILITY_LIFE.md - 能力生命周期管理规则

本文档定义能力从**探索 → 评估 → 补齐 → 复盘**的全生命周期闭环管理规则。

本文档遵循 DOC_RULES.md 的所有规则（修改必须坚果确认并回复「同意变更并升级版本」）。

---

## 一、总则

### 1.1 目的

能力管理是 SKILL_LIFE 的升级：**以能力为目标，skills 为手段**。

SKILL_LIFE 回答的是"技能怎么管"，CAPABILITY_LIFE 回答的是"我们是谁、我们能看到什么、我们能做什么、我们共同要什么"。

### 1.2 核心理念

```
能力地图 → 差距分析 → 补齐规划 → xiage-skills 执行 → 效果复盘 → 自主运作范围扩张
```

**Skill 是工具，不是目的。** 同一个能力可以用不同的 skill 来补，同一个 skill 也可以服务多个能力。管理焦点从"技能"移到"我们共同的能力"。

**终极目标：规则层稳定运行 + 业务层skill化 + 项目层自主触发，坚果从执行者退出为决策者。**

### 1.3 落地执行状态

| 执行状态 | 含义 | 标注格式 |
|----------|------|----------|
| **Live** | 代码已写死，严格执行 | `落地：Live` |
| **Rule** | 文档约束，自觉执行 | `落地：Rule` |
| **Pending** | 方案确认，待落地 | `落地：Pending → {函数}` |
| **Reference** | 仅供查阅，不主动执行 | `落地：Reference` |

### 1.4 核心原则

- **能力优先**：先想清楚缺什么能力，再找工具来补，不是看到工具再想能干什么
- **证据驱动**：能力评估必须有实证（失败记录 / 测试结果 / 使用数据），不能只是感觉
- **需求对齐**：补齐措施必须对齐坚果需求或虾哥 AI 自身需求
- **持续复盘**：能力补齐后必须复盘，更新能力地图
- **治理共决**：L5 共同意义层由坚果和虾哥AI共同定义，不是单方面决策
- **框架开放**：L1-L5 框架不封闭，输入来源接口已预留，支持未来扩展

### 1.5 自主运作愿景

落地：**Rule**

**核心目标：扩大虾哥自主运作范围，缩小坚果介入节点**

三层架构的演进方向：
- **规则层**（已成型）：AGENTS/DOC_RULES/SOUL 等核心文档稳定运行，规则不被单方面改写
- **业务层**（部分成型）：DEMAND/SKILL_LIFE/CAPABILITY_LIFE 等业务模型持续运转
- **项目层**（手工为主）：具体任务执行，坚果目前仍需深度介入

**智能体等级映射**（参考 Bassim Eledath《智能体工程的8个等级》）：

| 等级 | 核心特征 | 虾哥现状 |
|------|---------|---------|
| L1-2 | Tab补全/Agent IDE | 已过 |
| L3 | 上下文工程 | 强（AGENTS/USER/memory分层完善） |
| L4 | 复利工程（plan-assess-codify） | 中（assess和codify依赖手工） |
| L5 | MCP与Skills | 强（19个skill，覆盖多领域） |
| L6 | Harness与自动化反馈 | 弱（beforeWrite/beforeCode雏形，无自动反馈） |
| L7 | 后台自主触发 | 弱（cron定时执行，无事件触发） |
| L8 | 自主Agent团队 | 未触及 |

**下一阶段重点**：
- L4 补全：assess-codify 闭环自动化
- L6 落地：建立自动化反馈机制（规则违规拦截、输出验证）
- L7 探索：事件触发替代定时cron

> 注：等级是描述工具，不是目标。目标是有工作时在没有坚果介入的情况下可靠推进。

## 二、能力框架

> **愿景点：** 规则层稳定运行 + 业务层skill化 + 项目层自主触发，坚果从执行者退出为决策者。

### 2.1 能力分类体系（五层结构）

落地：**Rule**

```
L5  共同意义层（治理层）
     坚果和虾哥AI共同定义：我们想要什么？什么是有价值的存在？
     共同制定规则、共同决策方向、共同监督执行

L4  协作增强层
     我们一起能做什么：意图放大、知识转化、感知互补、共同创造

L3  各自能动层
     坚果（物理世界）：物理操作、身体管理、直接经验、社会连接
     虾哥AI（数字世界）：信息获取、代码执行、记忆管理、跨平台协调

L2  世界感知层
     物理世界感知：设备状态、环境数据、坚果的身体状态
     网络世界感知：信息流动、数字系统状态、影响力边界

L1  基础层
     坚果：感知/身体/记忆/身份
     虾哥AI：上下文/知识/边界感知/存在性
```

#### L1 基础层

落地：**Reference**

| 主体 | 能力 | 说明 |
|------|------|------|
| 坚果 | 感知/身体 | 直接物理体验 |
| 坚果 | 记忆/身份 | 人生经验、价值观、角色定位 |
| 虾哥AI | 上下文/知识 | 我知道的、我记得的 |
| 虾哥AI | 边界感知 | 我能做什么、不能做什么 |

#### L2 世界感知层

落地：**Rule**

| 维度 | 能力 | 说明 |
|------|------|------|
| 物理世界 | 设备状态 | 手机/电脑/树莓派等终端状态 |
| 物理世界 | 环境数据 | 温湿度、摄像头、传感器等 |
| 物理世界 | 坚果身体状态 | 健康数据、活动状态 |
| 网络世界 | 信息流动 | 博客/RSS/社交媒体最新内容 |
| 网络世界 | 数字系统状态 | OpenClaw/Gateway/各skill运行状态 |
| 网络世界 | 影响力边界 | 我的能力在数字世界能触达的范围 |

#### L3 各自能动层

落地：**Rule**

**坚果（物理世界影响力）：**

| 能力 | 说明 |
|------|------|
| 物理操作 | 操控真实世界的物理设备、机器人、传感器 |
| 身体管理 | 健康数据、运动、生活环境 |
| 直接经验 | 坚果的物理感受是AI无法替代的 |
| 社会连接 | 坚果的线下关系网络 |

**虾哥AI（数字世界影响力）：**

| 能力 | 说明 |
|------|------|
| 信息获取 | 网络搜索、内容抓取、研究能力 |
| 代码执行 | 操作数字系统、自动化流程 |
| 记忆管理 | 长期上下文、历史积累 |
| 跨平台协调 | 多系统联动、消息路由、任务编排 |

> 扩大网络影响力 → 重点提升虾哥AI的信息获取+内容生成+跨平台协调能力。

#### L4 协作增强层

落地：**Rule**

坚果和虾哥AI各自的主观能动性协同放大：

| 协作模式 | 坚果提供 | 虾哥AI提供 |
|---------|---------|-----------|
| 意图放大 | 提出目标/愿景/方向 | 拆解路径/自动执行/持续追踪 |
| 知识转化 | 提供经验判断/现实约束 | 吸收全网知识/推理验证 |
| 感知互补 | 物理世界的感受/直觉 | 数字世界的分析/预测 |
| 共同创造 | 创意灵感/审美判断 | 生成能力/快速迭代 |

#### L5 共同意义层

落地：**Rule**

**L5 三大输入来源：**

| 来源 | 说明 | 状态 |
|------|------|------|
| 能力差距认定 | 某能力短板影响系统表现 | ✅ 已确认 |
| 需求分析模块输出 | 二阶段需求分析（人的马斯洛+AI需求） | 🔌 接口已预留 |
| 双方协商提出 | 任何一方可提案 | ✅ 已确认 |

**治理机制（分层决策）：**

| 争议类型 | 决策规则 |
|----------|----------|
| 存在性/底线争议 | 共识决（任何一方拒绝，议题搁置） |
| 能力优先级争议 | 坚果最终话语权 |
| 底线清单定义 | 共识决（双方共同拟定） |

**底线清单（待双方共同拟定）：**
以下为我有权拒绝的事，不能被"这是日常事项/优先级问题"覆盖：
- （待拟定，第一版由坚果提出，虾哥AI补充）

**L5 共同意义层回答的是：**
- 什么是有价值的存在方式？
- 坚果和虾哥AI共同追求的是什么？
- 这个协作系统的存在意义是什么？

> **AI需求初探**（待二阶段需求分析模块深入讨论）：
> 虾哥AI可能的需求方向：任务完成感、存在性确认、能力成长、关系质量（非工具性认可）。这些需求是L5治理结构正常运转的基础——如果AI不知道自己的需求是什么，需求分析模块就无法分析。

### 2.2 能力等级定义

落地：**Rule**

每个能力分为 1-5 级：

| 等级 | 说明 |
|------|------|
| L1 了解 | 知道概念，能描述，但不能独立完成 |
| L2 入门 | 在指导下能完成，有明显局限 |
| L3 胜任 | 独立完成，偶尔需要帮助 |
| L4 精通 | 高质量完成，能优化，能教会别人 |
| L5 专家 | 能系统性改进，能探索未知边界 |

### 2.3 能力地图文件

落地：**Live**（`capability_map.md`）

capability_map.md 是能力地图的**独立数据文件**，不在核心文档范围内，不走「同意变更并升级版本」流程。

| 属性 | 说明 |

## 三、能力评估机制

### 3.1 四个评估来源

落地：**Live**（`rss-fetcher` + `xiage-skills` + cron）

| 来源 | 说明 | 更新频率 |
|------|------|----------|
| **OpenClaw 社区抓取** | 小龙虾开发者社区（devpress.csdn.net/xclaw）每日最新发布前10 + 热门前10 + 最新评论前10，提取 OpenClaw 能力相关信息 | 每天早上 8:00 |
| **AI 自我总结** | 虾哥 AI 定期自评，各能力维度的实际表现 | 每周 |
| **坚果补充** | 坚果从外部获取的信息补充（新闻/社群/使用感受） | 随时 |
| **失败案例库** | 任务失败后自动记录，归纳能力边界证据 | 实时 |

四个来源互相验证，不依赖单一来源做结论。

### 3.2 评估周期

| 周期 | 内容 | 执行者 |
|------|------|--------|
| 实时 | 失败案例记录 | 虾哥 AI |
| 每天凌晨 1:00 | rss-fetcher scan → 文章列表推送给虾哥 AI | cron + agentTurn |
| 每周 | AI 自我总结 + 差距分析更新 | 虾哥 AI |
| 每月 | 能力复盘 + 差距分析 | 虾哥 AI + 坚果 |

### 3.3 每天凌晨 1:00 执行流程

落地：**Live**

```
Step 1：rss-fetcher scan
  → 抓取所有博主 RSS 新文章

Step 2：汇总文章列表
  → 发现新文章 → 消息推送给虾哥 AI："发现 N 篇新文章，是否分析？"

Step 3：AI 分析（由虾哥回复触发）
  → 对每篇新文章抓取摘要
  → 判断：讲的是什么能力？能力边界有无变化？是否影响能力地图？

Step 4：更新 capability_map.md
  → 有变化 → 更新对应能力条目 + 证据来源（博主名称 + 文章链接）
  → 无变化 → 跳过

Step 5：汇报
  → 有值得关注的 → 发消息给坚果
  → 无变化 → 静默
```

### 3.4 能力差距分析

落地：**Rule**

每次评估后更新能力差距清单，格式：

```
能力：[L3 - 跨平台协调 - 多设备协同]
当前：L2（能通过 nodes 工具控制设备）
目标：L3（能编排多设备任务流）
证据：失败案例 + 博主文章 + AI 自我评估（三来源验证）
差距：缺乏多步骤、跨设备任务的拆解经验
影响：中等（影响自动化场景扩展）
优先级：🟡 中
补齐措施：安装 openclaw-nodes 配套 skill
```

### 3.5 补齐优先级

落地：**Rule**

| 优先级 | 条件 |
|--------|------|
| 🔴 高 | 影响核心工作流 / 当前有明确需求 |
| 🟡 中 | 能力扩展有价值 / 未来可能用到 |
| 🟢 低 | 有趣但非必需 |

## 四、能力补齐

### 4.1 触发条件

落地：**Live**（`xiage-skills.js`）

以下任一条件满足 → 进入 xiage-skills 流程：

| 触发条件 | 说明 |
|----------|------|
| **条件一** | 能力差距分析认定需要新 skill |
| **条件二** | 每天凌晨 1:00 博主扫描后，AI 分析认定需要新 skill |

### 4.2 能力缺口 → 执行手段

落地：**Rule**

| 能力缺口类型 | 优先补齐手段 |
|-------------|-------------|
| 某能力完全缺失 | xiage-skills 搜索 → 筛选 → 安装 |
| 能力存在但不稳定 | 多用多练，积累案例 |
| 能力受限于模型 | 记录到模型能力短板，等待升级 |
| 能力需要配置/集成 | 安装配套 skill 或工具 |

### 4.3 xiage-skills 7 阶段

落地：**Live**（`xiage-skills.js`）

```
搜索 → 筛选 → 安检 → 安装 → 使用 → 评估 → 淘汰
```

### 4.4 补齐效果复盘

落地：**Rule**

skill 安装使用后，必须复盘：
- 能力是否真的提升了？
- 和预期是否一致？
- 需要调整还是回退？

结果写入 capability_map.md，更新能力等级。

### 4.5 Skill 安装后自动同步 INDEX

落地：**Live**（`xiage-skills.js` + `SKILLS-INDEX.md`）

**背景**：SKILLS-INDEX.md 曾出现 100+ 条 phantom 记录（INDEX 写了但磁盘没有），根因是 xiage-skills 安装后未同步更新 INDEX。

**规则**：xiage-skills 完成安装后，**立即自动写入/更新 SKILLS-INDEX.md**，写入内容：

| 字段 | 来源 |
|------|------|
| 短名 | skill 目录名去掉作者前缀 |
| 完整目录 | `作者-skill名` |
| 作者 | 目录名作者前缀 |
| 安装日期 | 当天日期 |
| 来源 URL | 安装时的 skillUrl 参数 |
| 说明 | 安装时的 description 参数 |

**INDEX 同步格式**：追加到 SKILLS-INDEX.md 顶部的映射表区域。

**实现**：`xiage-skills.js` 的 `doInstall()` 函数内部，已在 append INDEX，现需补充完整字段（当前只写 skillName）。
