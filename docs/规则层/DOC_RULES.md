## 一、总则

### 1.1 目的

为所有文档建立统一的管理机制：分类清晰、结构规范、变更可追溯、规则能落地执行。

### 1.2 协作逻辑

**文档定规则 → 按规则执行 → 按规则演进**，DOC_RULES 是文档管理的最高约定，所有执行必须对齐本文档。

### 1.3 落地执行状态

| 执行状态 | 含义 | 标注格式 |
|----------|------|----------|
| **Live** | 代码已实现，严格执行 | `落地：Live` |
| **Rule** | 文档约束，自觉执行，待代码验证 | `落地：Rule` |
| **Pending** | 方案确认，待代码落地 | `落地：Pending → {函数}` |
| **Reference** | 仅供查阅，不主动执行 | `落地：Reference` |

### 1.4 触发词总表

#### 查询类

| 触发词 | 效果 | 执行 |
|--------|------|------|
| 「看XX文档」 | 展示一二级目录 | 内建 |
| 「看X.Y」 | 展开三级明细 | 内建 |
| 「看X.Y.Z」 | 给出该条款内容 | 内建 |
| 「看整个文档」 | 全量展示（最深层触发词） | 内建 |

#### 修改类

| 触发词 | 效果 | 执行 |
|--------|------|------|
| 「要改XX文档」 | 写待办到当日 memory | 内建 |
| 「同意变更并升级版本」 | 执行 beforeWrite → edit → 版本历史 → commit | beforeWrite.js |
| 「同意，生效」 | preCommitCheck → edit → execCommit | CODE_RULES |

#### 2.1.5 系统文档

落地：Rule

Gateway 运行时依赖的系统配置文件，与规则文档（2.1.1）共用同一套触发词「同意变更并升级版本」，但使用独立的存档机制。

| 系统文档 | 路径 | 存档脚本 | 恢复路径 |
|----------|------|----------|----------|
| Gateway 配置 | `C:\Users\Administrator\.openclaw\openclaw.json` | `scripts/archive-openclaw-config.ps1` | `C:\Users\Administrator\.openclaw\openclaw.json.bak.*` |
| Gateway 启动脚本 | `C:\Users\Administrator\.openclaw\gateway.cmd` | `scripts/archive-gateway-cmd.ps1` | `C:\Users\Administrator\.openclaw\gateway.cmd.bak.*` |
| PM2 进程配置 | `C:\Users\Administrator\.pm2\dump.pm2` | `scripts/archive-pm2-dump.ps1` | `C:\Users\Administrator\.pm2\dump.pm2.bak.*` |

**修改流程：**
1. 坚果确认「同意变更并升级版本」
2. `beforeWrite.js` 检测到系统文档，自动调用对应存档脚本
3. 执行 `edit` 修改文件
4. 系统文档无版本号，不走版本历史

**Health 修复时：** 从对应 `.bak.*` 时间戳文件（最新）恢复，不调 `pm2 restart`。

### 2.2 文档结构

#### 2.2.1 三级层级体系

落地：Rule

| 层级 | 格式 | 说明 |
|------|------|------|
| 一级 | `# 标题` | 文档主标题 |
| 二级 | `## 标题` | 主要章节 |
| 三级 | `### 标题` | 章节内的独立规则单元 |

禁止超过三级，禁止在正文使用四级或更深嵌套。

#### 2.2.2 文档头信息（强制）

落地：Live

每个规则文档头部必须包含：

```
落地：{状态}
当前版本：v{版本号}
最后更新：{YYYY-MM-DD}
```

#### 2.2.3 版本历史（强制）

落地：Live

每个规则文档必须包含版本历史表格：

```
## 版本历史

**当前版本：v{版本号}**

| 版本 | 日期 | 更新层级 | 详细变更 | 更新人 |
|------|------|----------|----------|--------|
| v1.0.0 | YYYY-MM-DD | 一级 | 初始版本 | 虾哥 |
```

### 2.3 Workspace 目录结构

落地：Rule

Workspace 采用「三层四区」结构，所有文件必须归入对应目录，不允许散落在根目录（OpenClaw 标准文件和目录除外）。

#### 2.3.1 标准目录（OpenClaw 内置）

| 目录 | 作用 | 规则 |
|------|------|------|
| `skills/` | 所有技能（含自写+第三方） | 按 OpenClaw 标准加载，不新建顶层子分组 |
| `memory/` | 每日对话日志 | OpenClaw 标准目录，按日期自动归档 |

#### 2.3.2 根目录白名单

根目录保留以下文件，其余文档类文件必须归入 `docs/`：

- OpenClaw 配置文件：`SOUL.md` / `USER.md` / `IDENTITY.md` / `AGENTS.md` / `HEARTBEAT.md` / `BOOTSTRAP.md`
- 长期记忆：`MEMORY.md`
- 技能索引：`SKILLS-INDEX.md`

#### 2.3.3 项目创建规则

新建项目时，必须在 `docs/项目层/<项目名>/` 下创建项目目录，后续所有项目文件（含运行时数据）置于该目录下，不得在根目录散落。

### 2.4 归档规则

#### 2.4.1 归档触发条件

落地：Rule

以下情况触发归档：
- 文档被新版本完全替代
- 临时文件确认无用
- 文档功能已迁移至其他位置

#### 2.4.2 归档执行

落地：Live（`beforeWrite.js` 自动执行）

归档操作：
1. 将当前版本复制到 `old-versions/{文档名}.v{版本号}-{日期}`
2. 对文档类文件，同步移动到 `docs/archive/` 或 `scripts/archived/`

## 三、操作流程

### 3.1 变更流程（文档修改）

落地：Live

**收到「同意变更并升级版本」后：**

1. 运行 `beforeWrite.js`（存档 + 格式检查）
2. 执行 `edit` 修改文件
3. 追加版本历史行（版本号+1）
4. `git add` → `git commit` → `git push`

#### 3.1.1 写入前检查（preWriteCheck 逻辑）

落地：Live（`beforeWrite.js`）

**格式检查：**
- [ ] 文档头部三字段完整（落地/版本/更新日期）
- [ ] 版本历史表格存在且格式正确
- [ ] 新建文档：落地标注 + 版本号 v0.0.1

**路径合规检查（新增）：**
- [ ] 新建文件在规定目录下（docs/ / skills/ / memory/）
- [ ] 核心文档（2.1.1 列表）未被删除或移动

**内容合规检查（新增）：**
- [ ] Workspace 目录结构合规（2.3）
- [ ] 文档分类正确（2.1）

#### 3.1.2 违规处理

落地：Live

| 违规类型 | 处理方式 |
|----------|----------|
| 格式缺失 | 拒绝写入，提示补全 |
| 路径不合规 | 拒绝写入，提示正确路径 |
| 核心文档被删 | 拒绝操作，报告坚果 |

---

### 3.2 过期清理

落地：Rule

| 清理对象 | 条件 |
|----------|------|
| `old-versions/` 历史文件 | 同一文档保留最近 5 个版本 |
| `docs/archive/` 文档 | 超过 1 年无访问则标记废弃 |
| `memory/` 日志 | 按日期自动归档，不手动清理 |
