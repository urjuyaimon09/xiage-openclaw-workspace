# SKILL_LIFE.md - 技能生命周期管理规则

本文档定义技能从**搜索 → 筛选 → 安检 → 安装 → 使用 → 评估 → 淘汰**全生命周期闭环管理规则。

本文档遵循 DOC_RULES.md 的所有规则（修改必须坚果确认并回复「同意变更并升级版本」）。

---

## 一、总则

### 1.1 目的

为技能全生命周期建立系统化管理机制：保持能力纯净，只留有用的，淘汰没用的，持续进化不臃肿。

### 1.2 文档定位（与 CAPABILITY_LIFE 共存）

| 文档 | 管什么 | 回答什么问题 |
|------|--------|-------------|
| CAPABILITY_LIFE.md | 能力层 | 我们缺什么能力？用什么手段补？效果如何？ |
| SKILL_LIFE.md | 技能层 | skill怎么管？安检怎么做？记录什么？怎么评估淘汰？ |

能力是**目标**，skill是**手段**。两者独立运作，互不覆盖。

### 1.3 协作逻辑

**文档定规则 → 按规则执行 → 按规则演进**，SKILL_LIFE 是技能管理的最高约定，所有执行必须对齐本文档。

### 1.4 落地执行状态

| 执行状态 | 含义 | 标注格式 |
|----------|------|----------|
| **Live** | 代码已写死，严格执行 | `落地：Live` |
| **Rule** | 文档约束，自觉执行，待代码验证 | `落地：Rule` |
| **Pending** | 方案确认，待代码落地 | `落地：Pending → {函数}` |
| **Reference** | 仅供查阅，不主动执行 | `落地：Reference` |

### 1.5 核心原则

- **坚果主权**：规则变更、重大技能架构调整必须坚果确认
- **安全第一**：永远把安全放第一位，可疑技能直接不装
- **宁缺毋滥**：没用的技能及时下，不占上下文，不添乱
- **持续进化**：小步快跑，每周整理，能力越来越精，不会越来越臃肿
- **修改透明化**：对现有脚本/规则做修改后，必须输出变更摘要（改了什么、为什么改）

## 二、生命周期流程

落地：Rule

### 2.1 九阶段总览

```
搜索 → 筛选 → 编写 → 安检 → 安装 → 实测 → 使用 → 评估 → 淘汰
  ↑                                                          │
  └──────────────────── 循环迭代 ←───────────────────────────┘
```

> 编写是搜索/筛选的兜底：搜不到合适的 → 自己写 → 继续走完后续生命周期。

### 2.2 搜索规则

落地：**Live**（`xiage-skills.search()`）

三个来源，各取 ≥ 100 条：

| 来源 | 获取方式 | 排序 | 最低要求 |
|------|----------|------|----------|
| skills.sh 24h 趋势 | 浏览器渲染提取 | 按 24h 热度 | ≥ 100 条 |
| skills.sh 总下载 | 浏览器渲染提取 | 按总下载量 | ≥ 100 条 |
| ClawHub 总下载 | 浏览器渲染提取 | 按总下载量 | ≥ 100 条 |

三个来源均达到最低要求后，进入筛选。

### 2.3 筛选规则

落地：**Live**（`xiage-skills.filter()`）

筛选优先级：
1. **能力互补**：解决现有问题、扩展不存在的能力、不重复已有技能
2. **相关性**：和日常工作、自我提升直接相关
3. **流行度**：ClawHub ≥ 1k installs / skills.sh ≥ 1k clicks
4. **清晰度**：描述清晰，用法明确

直接跳过：已安装 / 功能重复 / 零下载 / 描述模糊 / **同名不同作者**

> **同名不同作者规则**：候选列表中，同名 skill 来自不同作者时，仅保留下载量最高的一个，其余筛出。这是为了避免同名 skill 堆积，同一功能只保留最受欢迎的实现。

筛选配额：

| 来源 | 最大候选数量 |
|------|------------|
| ClawHub 总下载 | 最多 5 个 |
| skills.sh 24h 趋势 | 最多 5 个 |
| skills.sh 总下载 | 最多 5 个 |

总候选不超过 15 个。

### 2.3 编写规范

落地：Rule

> **触发条件**：搜索/筛选找不到合适的 Skill → 自己写。  
> 写完后必须走安检，继续后续生命周期，不能跳过。

#### 2.3.1 编写前：定义评估标准

自编写 Skill 必须先定义评估用例，再实现：

```yaml
# skills/<author-skill>/EVAL.yaml
- skills: [<skill名>]
  query: <用户输入示例>
  files: [<测试文件路径，可为空>]
  expected_behavior:
    - <具体可验证的预期行为1>
    - <具体可验证的预期行为2>
```

至少 3 个评估用例，覆盖正常路径 + 边界情况 + 失败路径。

#### 2.3.2 开发流程

```
编写 EVAL.yaml（定义成功标准）
  → 实现 Skill
  → 按 expected_behavior 逐条验证
  → 全部通过 → 进入安检
  → 未通过 → 迭代修复
```

#### 2.3.3 主文件规范

| 规则 | 标准 |
|------|------|
| 主文件行数 | SKILL.md 正文 ≤500 行（不含元数据头部） |
| 引用深度 | 文件引用限一层（SKILL.md → 子文件），禁止子文件再引用子文件 |
| name 字段 | ≤64 字符，仅小写字母、数字、连字符 |
| description 字段 | ≤1024 字符，必须说明"能做什么"+"何时使用" |

#### 2.3.4 工作流规范

| 规则 | 标准 |
|------|------|
| 步骤编号 | 复杂任务使用 "Step 1 / Step 2 / ..."，不允许长段落叙述 |
| 验证节点标注 | 关键操作前标注"立即验证：`command`"，不允许跳步 |
| 反馈循环 | 验证失败时明确"返回 Step X 重试"，不允许静默继续 |
| 默认推荐 | 多种工具可选时，直接给出默认推荐 + 备用方案 |

#### 2.3.5 脚本规范

| 规则 | 标准 |
|------|------|
| 路径风格 | 使用正斜杠（`/`），禁止 Windows 反斜杠（`\`） |
| 依赖声明 | 在 SKILL.md 中明确列出所需依赖，不假设环境已有 |
| 魔法数字 | 硬编码数值必须加注释说明用途，禁止无解释常量 |
| 错误处理 | 脚本必须包含错误处理，不允许裸奔执行 |

#### 2.3.6 脚本归属规则

**脚本不能独立存在，必须归属于某个 Skill。**

- 新建脚本：必须在某个 Skill 目录下，不允许在 workspace 根目录散落
- 现有散落脚本：本次一并清理，归入最接近的 Skill 目录；无法归类的评估后淘汰
- 跨 Skill 共用脚本：提取为独立 Skill，或放入公共目录并登记

### 2.4 安检规则

落地：**Live**（`xiage-skills.securityCheck()`）

🔴 任一红 Flag 直接拒绝：
- `curl/wget` 拉取未知远程代码直接执行
- 外传敏感数据（memory、用户信息、系统配置）
- base64 解码后执行
- `eval/execute` 外部输入
- 修改工作区外系统文件
- 请求 sudo/管理员权限
- 访问浏览器 cookie/session
- **魔法数字**：脚本里未解释的硬编码常量（无注释说明的数值）
- **缺失依赖声明**：SKILL.md 中未明确列出所需包/工具

🟢 低风险：纯文档/代码片段 → 直接安装
🟡 中风险：文件操作/简单网络 → 报告用户，确认后安装

**ClawHub fallback 规则**（v1.3.0 新增）：
git clone 失败时，自动 fallback 到 ClawHub 页面抓取 + 文本规则扫描。17条红 Flag 规则直接作用于页面文本，无需 git clone。

### 2.5 安装规则

落地：**Live**（`xiage-skills.install()`）

安装路径：`skills/{author}-{skill-name}/`

**skills.sh 来源 Fallback 链（按可靠性排序）：**

1. skills.sh 页面文本抓取（stealth 浏览器渲染页面，直接提取 SKILL.md 内容，最可靠）
2. monorepo 预下载缓存提取（需 670MB ZIP 下载，易卡）
3. GitHub API 单仓库下载（skills.sh skill 无独立 GitHub 仓库，基本失败）
4. ClawHub puppeteer stealth 下载 → 页面文本抓取（保底，至少写一个 SKILL.md 不空跑）

**GitHub 来源 Fallback 链（按可靠性排序）：**

1. ClawHub ZIP API（stealth 浏览器获取下载链接，**CDP 浏览器下载**，最可靠）
2. GitHub API zipball 下载
3. ClawHub 页面文本抓取（保底）

**网络限制说明**（v1.9.0 新增）：
- exec 工具对 Node.js `https.get()` 发出的 HTTP 请求全部封锁（EPERM）
- **CDP 浏览器下载是唯一可靠的 ZIP 下载方式**：通过 Chrome DevTools Protocol 的 `Page.setDownloadBehavior` 让浏览器自己发出下载请求，绕过 exec 封锁
- skills.sh 页面文本抓取不走 exec，走 puppeteer stealth 浏览器，不受影响

**stealth 爬虫特性**（v1.4.0 新增）：
- puppeteer-extra + stealth 插件
- 随机 UA / 视口
- humanLikeScroll 真人类滚动模拟
- 3次导航重试

**保底机制**（v1.4.0 新增）：
ZIP 也失败时，直接写 SKILL.md，不空跑。

### 2.6 使用规则

落地：**Live**

使用前：必须先读技能的 `SKILL.md`，严格遵循技能规则执行。

使用后立即记录到 `skills/xiage-skills/metadata/skill-usage.json`：

```
node xiage-skills.js use <skill名> success|fail [备注]
```

同时追加当日 `memory/YYYY-MM-DD.md`：
- 使用场景
- 执行结果
- 是否解决问题

#### 2.6.1 实测机制

落地：**Live**（`xiage-skills.fieldtest()`）

**触发方式：**
- **新安装触发**：skill 安装完成后自动触发，无需人工干预
- **单独调用**：`node xiage-skills.js fieldtest <author/skillname>`
- **定时触发**：每日早上 7:00（cron）

**实测字段（对齐 SKILLS-INDEX.md 主索引表）：**

| 字段 | 说明 |
|------|------|
| 能力类型 | 提取/生成/分析/执行/转换/监控 |
| 触发场景 | 遇到什么问题时该用 |
| 能力边界 | 不能处理什么 |
| 组合推荐 | 适合与哪些skill串联 |
| 实测状态 | 最近一次实测时间+结果 |
| 可用性 | 🟢正常/🟡待测/🔴失效 |

**实测流程：**
1. 读取 SKILL.md，理解用法
2. 执行 skill 脚本，验证各功能
3. **验证中间产物**：如果 skill 输出中间文件（如 JSON/结构化数据），必须验证其正确性，不允许跳过验证直接使用最终输出
4. 记录能做什么 / 不能做什么 / 坑
5. 输出到 `skills/xiage-skills/metadata/SKILL-FIELD-TESTS.md`

**实测结果文件：** `skills/xiage-skills/metadata/SKILL-FIELD-TESTS.md`

### 2.7 评估规则

落地：**Live**（cron 定时 + `xiage-skills.evaluate()`）

**触发方式：**
- **每周五下午 4 点**自动评估（id: 3c68d0da）
- 手动触发：`node xiage-skills.js evaluate`

四维度打分：

| 维度 | 说明 |
|------|------|
| 使用率 | 过去一周使用次数 |
| 实用性 | 完全解决/部分解决/未解决 |
| 稳定性 | 是否出过失败/错误 |
| 维护性 | 作者一年内是否有更新 |

综合评级：🟢正常 / 🟡观察 / 🔴淘汰

报告输出到 `skills/xiage-skills/metadata/SKILLS-EVALUATION.md`。

### 2.8 淘汰规则

落地：**Live**（`xiage-skills.retire()`）

触发条件（满足任一）：
- 连续三个月无使用记录
- 连续两次评估实用性=0
- 作者停止维护超过一年
- 安检发现红 Flag

淘汰操作：
1. 从 `SKILLS-INDEX.md` 移除
2. 本地文件移入 `skills/retired/` 归档

**淘汰前复核**：
无替代技能 → 只标记「待替换」，不实际删除。
有替代且需要 → 实际删除。

## 五、版本与维护

### 5.1 版本号规则（严格三级）

落地：Rule

遵循 SemVer 语义化版本：
- **Major（第一位）**：架构/流程大改，不兼容旧版 → `1.0.0` → `2.0.0`
- **Minor（第二位）**：新增功能/规则调整 → `1.0.0` → `1.1.0`
- **Patch（第三位）**：bug 修复/规则修正 → `1.0.0` → `1.0.1`

落地：Rule
