本文档记录虾哥 AI 架构的演进历程、关键决策、技术原理和未来方向。

## 一、架构总览

```
用户输入
  ↓
QueryEngine（OpenClaw 内核）
  ↓
Agent Loop
  ├─ 工具调用（Tool Use）
  │    └─ 并发优化（sessions_spawn 子 Agent 并行）
  │
  ├─ 5层压缩（xiage-context-engine）
  │    ├─ Layer1: 工具结果外部化
  │    ├─ Layer2: 消息打分 + MERGE（核心）
  │    ├─ Layer3: 部分压缩
  │    ├─ Layer4: 折叠旧窗口
  │    └─ Layer5: Memory Flush
  │
  ├─ Minimax 缓存续命（ping-loop + Windows计划任务）
  │
  └─ 上下文窗口（MiniMax 200K token）
```

## 二、关键决策记录

### 2.1 为什么选择 Minimax 而非 Claude

| 维度 | Minimax | Claude |
|------|---------|--------|
| 成本 | 更低（M2.7 $3/MTK） | 更贵 |
| Token 窗口 | 200K（更大） | 200K |
| Prompt Cache | ✅ 5分钟 TTL | ✅ 1小时 TTL |
| API 稳定性 | 国内访问更稳定 | 需代理 |
| OpenClaw 集成 | 原生支持 | 需额外配置 |

**决策**：性价比优先，MiniMax 是当前最优选择。

### 2.2 为什么做5层压缩而不是依赖大上下文窗口

- 大上下文窗口不等于低 cost
- 每次上传全部历史 = 每次付全额 token
- 压缩 = 只付增量 = 降低成本
- 200K 窗口是上限，不能无限依赖

### 2.3 为什么做 MERGE 而不是删除低分消息

**错误做法（删除）**：
```
[A, B, C, D, E] → [A, D, E]  // B,C被删除 → 位置前移
D的前缀变了 → Minimax 缓存断裂 → 每次都要重建缓存
```

**正确做法（MERGE）**：
```
[A, B, C, D, E] → [A, SUMMARY(B+C), D, E]
                   ↑
             B+C被合并成一条摘要，替换原位置
A的前缀完全不变 → 缓存持续命中 → 增量写入
```

**结论**：MERGE 保留了前缀结构，是 Claude Code 的核心设计。删除消息等于主动破坏缓存。

### 2.4 为什么用 ping-loop 而不是 cron/autoRefresh

| 方案 | 问题 |
|------|------|
| cron systemEvent → main | systemEvent 不触发 LLM，缓存不刷新 |
| cron agentTurn → isolated | 刷新的是 isolated session 缓存，不是主会话 |
| /heartbeat start | OpenClaw 内部定时器，会话卡死 |
| autoRefresh | 当前版本不存在（schema 无此字段） |
| **ping-loop.js** | ✅ sessions_send → 主会话触发 LLM → 缓存刷新 |

**决策**：外部脚本直接调 `openclaw sessions send`，最稳定可靠。

### 2.5 为什么分层记忆（hot/warm/cold）

| 层级 | 内容 | 触发 |
|------|------|------|
| hot | current.md + lessons.md | 每次启动必读 |
| warm | memory/YYYY-MM-DD.md | 今天+昨天启动时加载 |
| cold | memory/cold/archive.md | 按需引用才加载 |

**决策**：不是所有记忆都需要每次加载，分层节省 token。

## 三、技术实现

### 3.1 5层压缩原理（xiage-context-engine）

#### Layer1：工具结果外部化
- 工具返回 > 2000 字 → 写入磁盘临时文件
- 上下文只保留文件路径引用
- 需要时按需加载

#### Layer2：消息打分 + MERGE（核心创新）
**打分规则**：
```
+3  用户消息（保留）
+5  含"同意"/"结论"/"决定"的assistant消息（保留）
+2  有工具调用的assistant消息（保留）
-1  纯工具返回（tool role）
-3  错误信息
-1  过短内容（<20字符）
```

**MERGE 流程**：
1. 扫描消息，识别连续低分区段（score <= 0）
2. 调用 MiniMax 生成这段的摘要（非阻塞，8秒超时）
3. `messages.splice(start, blockSize, summaryMsg)` — 一条替换一段
4. 前缀结构完整，缓存持续命中

#### Layer3：微压缩（cache_edits 注意力屏蔽）
**原理**（与我们的理解完全不同）：
- Claude 用 `cache_edits` 参数在**服务端**屏蔽旧工具结果的 attention
- 旧 token 物理位置不变，KV 缓存全部有效，只是 attention mask = 0
- 本地消息**完全不动**，动了就会导致下次请求的序列改变，缓存失效
- 有两种模式：
  - **时间触发**：cache 已过期（>60分钟），直接修改本地消息
  - **热缓存模式**：cache 仍有效，通过 attention mask 屏蔽旧内容
- **关键理解**：cache_edits 不是删除 token，而是让它们在 forward pass 中"透明"
- 可清理工具：Read、Bash、Grep、Glob、WebSearch、WebFetch、FileEdit、FileWrite

**我们的差距**：Minimax Messages API 没有等价于 `cache_edits` 的参数。**Layer3 原版功能我们完全无法实现**。我们用 Layer2 MERGE 达到类似效果（减少 token 量），但不是注意力屏蔽。

#### Layer4：折叠旧窗口
- context 消耗 >= 90% 时触发
- 前半部分压缩为结构化摘要
- 写入 memory/hot/current.md

#### Layer5：Memory Flush
- 委托给 memory-flush 插件处理
- 会话临近压缩时触发

### 3.2 Minimax 缓存 TTL 续命原理

**Minimax Prompt Cache 机制**：
- TTL：5 分钟
- 触发：输入 > 512 token
- 价格：读取 ≈ 输入价的 1/10

**ping-loop 外部心跳**：
```
每 4 分钟
  → sessions_send "[AUTO_REFRESH] ping" 到主会话
  → 主会话触发 LLM 调用
  → 命中缓存前缀 → TTL 刷新
  → SOUL.md 规则10：收到 [AUTO_REFRESH] → 回复 NO_REPLY（静默）
```

**完整收益**：
- ping-loop 维持 TTL → 缓存不断
- Layer2 MERGE → 前缀不变 → 缓存命中
- 两者结合 → 等同 Claude Code 1小时缓存效果

#### 3.2.1 组件架构

| 组件 | 类型 | 职责 |
|------|------|------|
| xiage-context-engine | OpenClaw 插件 | Layers 1-4 压缩逻辑 |
| ping-loop.js | 外部独立 Node 进程 | 每4分钟 sessions_send 刷新缓存 |
| start-ping-loop.bat | Windows 批处理 | ping-loop 启动入口 |
| Windows 计划任务 | 系统级 | 用户登录时自动触发 ping-loop |
| SOUL.md 规则10 | 规则文档 | 收到 [AUTO_REFRESH] → NO_REPLY 静默 |

#### 3.2.2 自动启动机制

**为什么不能集成到插件**：
- detached 子进程无法在 gateway restart 后存活
- Windows 上 `openclaw gateway restart` 会杀整个进程树
- detached 只保证"父进程正常退出时子进程存活"，不保证"父进程被杀死时存活"

**Windows 计划任务**（用户登录时触发）：
```
用户开机 → 登录 Windows → 计划任务"虾哥PingLoop"触发 → start-ping-loop.bat → ping-loop.js 启动
```

| 文件 | 路径 |
|------|------|
| ping-loop.js | `skills/minimax-cache-autorefresh/ping-loop.js` |
| start-ping-loop.bat | `skills/minimax-cache-autorefresh/start-ping-loop.bat` |
| xiage-context-engine | `extensions/xiage-context-engine/` |
| 计划任务 | `虾哥PingLoop`（Windows 任务计划程序）|

### 3.3 子 Agent 并行原理

**触发条件**：
- 需要并行执行 >= 2 个独立的 read-only 工具调用

**调用方式**：
```
sessions_spawn({
  task: "read files",
  runtime: "subagent",
  mode: "run",
  silent: true
})
```

**并发安全工具白名单**：
- Read / Glob / Grep / WebSearch / WebFetch / Image / Bash(读命令)

**非并发安全（必须串行）**：
- Edit / Write / Move / Delete / Bash(写命令)

**约束**：`subagents.maxConcurrent = 5`

### 3.4 冷热记忆分层原理

**加载时机**：
```
Session Startup：
  1. 读 SOUL.md → 确定身份
  2. 读 USER.md → 确定用户
  3. 读 memory/hot/current.md → 热记忆（当前状态）
  4. 读 memory/hot/lessons.md → 热记忆（教训）
  5. 读 memory/YYYY-MM-DD.md（今天+昨天）→ 温记忆
  6. 读 MEMORY.md → 索引入口
```

**写入规则**：
- 记结论不记过程
- 标签化（#tag1 #tag2）
- 教训优先（踩坑后立即写 lessons.md）
- MEMORY.md 只存精华（太长就归档）

## 四、踩坑教训（Lessons）

### 4.1 源码修改风险 ⚠️ 最高优先级
- 任何时候修改 OpenClaw 源码前必须先问坚果
- 源码改名/删除导致 gateway 完全崩溃（无回滚）
- 改之前必须备份原始文件

### 4.2 cron 架构限制
- main session cron 硬性要求 `payload.kind="systemEvent"`
- systemEvent 不触发 LLM 调用
- agentTurn 只支持 isolated session
- **教训**：cron systemEvent → isolated session 无法刷新主会话缓存

### 4.3 Layer2 LLM 调用超时问题
- 调用 MiniMax 生成摘要不能无限等待
- 必须设置 8 秒超时 + 规则兜底摘要
- 否则会卡住网关，导致超时连锁反应

### 4.4 gateway 重启 kill 所有子进程
- ping-loop.js 是独立 Node 进程
- gateway restart 会 kill 所有子进程
- 需要重启后手动拉起

### 4.5 OpenClaw 版本配置兼容性
- `contextPruning` 是有效路径（schema 有）
- `autoRefresh` 在 schema 中不存在（新版本功能）
- 改 openclaw.json 前必须 `openclaw gateway status` 验证

### 4.6 MiniMax API 缓存字段名
- 响应字段是 `cache_read_input_tokens`（不是驼峰）
- 只有 Messages API（/anthropic/v1/messages）+ `cache_control: ephemeral` 才能触发缓存

## 六、实测数据（2026-04-06）

### 6.1 缓存命中率

**测试条件**：
- 模型：MiniMax-M2.7-highspeed
- 上下文：133K tokens（65% 使用率）
- ping-loop 间隔：4分钟
- 连续运行：14轮

**结果**：

| 指标 | 值 |
|------|-----|
| cacheRead | 133,354 token |
| totalTokens | 133,515 token |
| **缓存命中率** | **99.9%** |
| cacheWrite | 0 token（无重建）|
| 单条 cost | ~$0.008 |
| 响应时间 | 4.5-7.4秒（稳定）|
| ping-loop 成功率 | 14/14（100%）|
| 网关稳定性 | 无崩溃 |

**结论**：MERGE + ping-loop 方案完全生效，缓存持续命中，网关稳定运行。

### 6.2 与 Claude 效果对比

| 指标 | Claude Code | 我们的方案 |
|------|------------|----------|
| 缓存 TTL | 1小时 | 5分钟（ping-loop 续命）|
| 缓存命中率 | ~95% | **99.9%** |
| 响应时间 | 不稳定 | **4.5-7.4秒稳定** |
| 前缀保护 | 删除破坏前缀 | **MERGE 保留前缀** |

**意外发现**：我们的 MERGE 方案比 Claude Code 的删除方案缓存命中率更高，因为 MERGE 完整保留了前缀结构。

## 七、组件整合计划

### 7.1 当前组件分布

| 组件 | 类型 | 职责 |
|------|------|------|
| xiage-context-engine | OpenClaw 插件 | Layers 1-4 |
| ping-loop.js | 外部独立进程 | 缓存 TTL 续命 |
| start-ping-loop.bat | Windows 启动脚本 | ping-loop 入口 |
| Windows 计划任务 | 系统级 | 用户登录时自动启动 ping-loop |
| memory-flush | 不存在 | Layer 5 |
| SOUL.md 规则10 | 规则文档 | AUTO_REFRESH 静默 |

### 7.2 为什么 ping-loop 是独立进程

**关键测试**：detached 子进程无法在 gateway restart 后存活。
- Windows 上 `openclaw gateway restart` 会杀整个进程树
- `detached: true` 只保证父进程正常退出时子进程存活
- 不保证父进程被杀死时子进程存活

**结论**：ping-loop 必须是独立进程，不能集成到 xiage-context-engine 插件内部。

### 7.3 自动启动方案

**Windows 计划任务**：用户登录时自动触发 ping-loop
```
schtasks /create /tn "虾哥PingLoop" /sc onlogon /tr "node ping-loop.js"
```

**启动链路**：
```
用户开机 → 登录 Windows → 计划任务触发 → start-ping-loop.bat → ping-loop.js 启动
```
